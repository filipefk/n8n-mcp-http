# CLAUDE.md

Este arquivo fornece orientações para o Claude Code (claude.ai/code) ao trabalhar com o código deste repositório.

## Visão Geral

N8nMcpHttp é um servidor MCP (Model Context Protocol) em .NET 10 ASP.NET Core que expõe a API REST do n8n (workflows, data tables, execuções, tags) como ferramentas MCP via transporte HTTP, montado em `/mcp`.

## Build e Execução

```
dotnet build N8nMcpHttp.slnx
dotnet run --project src/Backend/N8nMcpHttp/N8nMcpHttp.csproj
```

```
dotnet test tests/McpTests/McpTests.csproj
```

Projeto de testes em `tests/McpTests` (xUnit), cobrindo o `McpToolkit` (`McpClient`, as cinco classes de tools — `WorkflowTools`, `DataTableTools`, `ExecutionTools`, `TagTools`, `BackupTools` —, `BackupService`, e o namespace `McpToolkit.Shell`). `McpClient`, `BackupService` e as classes de `Shell` são `sealed` sem interfaces — os testes instanciam as classes reais e fakeiam só as bordas: um `FakeHttpMessageHandler` escrito à mão (`Fakes/FakeHttpMessageHandler.cs`, sem dependência de mocking framework) no lugar da API REST do n8n, um `FakeRequestContext` (`Fakes/FakeHostEnvironment.cs`) no lugar de `IRequestContext`, e um diretório temporário real para o `BackupService`. Cobertura completa nos pontos com lógica própria (`ResolveTarget`, `FilterWorkflowPayload`, os quatro métodos de edição de node — incluindo o religamento de conexões preservando ramos de IF/Switch e a preservação de conexões de IA não relacionadas —, `ResolveWorkflowId`, os helpers de sumarização em `McpToolsHelpers`, `BackupService` inteiro, incluindo sanitização de nome de arquivo, `ResolveBackupPath` e `DeleteBackup`, o round-trip de `restore_data_table_backup`/`delete_backup` — incluindo a ordem criar-antes-de-excluir —, e `Shell/` inteiro — `ShellResolver`, allow/blocklist do `ShellCommandRunner` incluindo comandos encadeados e quebra de linha, teto de timeout, truncagem, timeout real de processo, e a checagem de senha do `ShellTools`, executando comandos reais e triviais no shell do SO); os métodos de CRUD simples (tags, data tables, execuções) têm só 1-2 testes representativos por família. O projeto de testes referencia apenas `McpToolkit.csproj`, então nada do host entra nos testes: os endpoints HTTP (`GET /backups/{fileName}`, `/api-key/*`, `/health`), o `McpApiKeyMiddleware`, o `McpTrafficLoggingMiddleware`, o rate limit, a página `wwwroot/index.html` e o `ApiKeyGenerator` (projeto `GeraApiKey`) não têm teste automatizado (não há `WebApplicationFactory` no projeto) — validação é manual, com a coleção do Postman na raiz do repositório.

## Arquitetura

```
src/Backend/GeraApiKey/    — biblioteca do gerador de API Key
src/Backend/McpToolkit/    — biblioteca McpToolkit
src/Backend/N8nMcpHttp/    — host ASP.NET Core
tests/McpTests/            — projeto de testes xUnit
```

Três projetos de código, mais um de testes:

- **GeraApiKey** (`src/Backend/GeraApiKey`) — biblioteca sem nenhum pacote, referenciada só pelo host. `ApiKeyGenerator.cs` junta uma lista de strings numa única key segura para header HTTP e desfaz a key devolvendo os valores na mesma ordem: `join` por U+001F (Unit Separator) → UTF-8 estrito → 1 byte de semente aleatória no início → XOR com um keystream xorshift32 derivado dessa semente → `Base64Url.EncodeToString` (alfabeto `A-Za-z0-9-_`, sem padding). O XOR é involutivo, então decodificar é aplicá-lo de novo com a mesma semente; a semente aleatória faz a mesma lista gerar keys diferentes e esconde prefixos reconhecíveis (`https://`). É **ofuscação, não criptografia** — não há segredo no algoritmo, quem conhece reverte, então a key gerada é um segredo. A biblioteca é agnóstica de domínio: só vê `IEnumerable<string>`; a ordem dos valores vive em `McpApiKey.cs`, no host.

- **McpToolkit** (`src/Backend/McpToolkit`) — biblioteca de classes sem nenhuma dependência de ASP.NET Core (nem `FrameworkReference`) — só `Microsoft.Extensions.Options`/`Hosting.Abstractions` e o SDK MCP. Contém:
  - `McpClient.cs` — o único lugar que se comunica com a API REST do n8n. Encapsula o `HttpClient`, monta as requisições e expõe um método assíncrono para cada operação da API do n8n (workflows, data tables, execuções, tags), incluindo métodos compostos de edição granular de node (`UpdateWorkflowNodeAsync`, `AddWorkflowNodeAsync`, `DeleteWorkflowNodeAsync`, `RenameWorkflowNodeAsync` — todos fazem GET → transforma em memória → PUT via `FilterWorkflowPayload`, no mesmo padrão de `UpdateWorkflowAsync`). Todas as respostas são `JsonNode?` brutos. Erros HTTP não-2xx lançam `N8nApiException` (`StatusCode` + `Body`, truncado em 2000 chars), não mais `InvalidOperationException` com o corpo embutido na mensagem.
  - `N8nApiException.cs` — exceção tipada para erros da API do n8n, permite filtrar por `StatusCode` (ex: `HttpStatusCode.NotFound`) em vez de checar substring "404" na mensagem.
  - `IRequestContext.cs` / `HttpRequestContext.cs` (esta última no host) — abstrai o acesso à requisição HTTP em curso para que a biblioteca não dependa de `IHttpContextAccessor` **nem do formato do header `x-api-key`**: expõe `N8nUrl`/`N8nApiKey` (os valores que o cliente mandou) e `GetRequestBaseUrl()` (para montar links de backup). Quem decodifica o header é o `HttpRequestContext`, no host. `McpClient.ResolveTarget()` e `BackupTools` recebem `IRequestContext` via DI.
  - `WorkflowTools.cs`, `DataTableTools.cs`, `ExecutionTools.cs`, `TagTools.cs`, `BackupTools.cs` — a superfície voltada ao MCP, uma classe `[McpServerToolType]` por família (antes era uma única `McpTools.cs` com 44 tools). Cada família pode ser ligada/desligada independentemente via configuração (`Tools:Workflows:Enabled`, `Tools:DataTables:Enabled`, `Tools:Executions:Enabled`, `Tools:Tags:Enabled`, `Tools:Backups:Enabled` — todas `true` por padrão), no mesmo padrão de `Shell:Enabled`. Os parâmetros de ferramentas que representam estruturas JSON (nodes, connections, settings, filters, rows) são tipados como `JsonObject`/`JsonArray` diretamente (o SDK MCP gera `"type":"object"`/`"array"` no schema a partir deles) — não mais strings JSON escapadas com sufixo `_json`. `McpToolsHelpers.cs` concentra os helpers compartilhados entre as cinco classes: `Json(...)` (substitui `?? "{}"` repetido), `ResolveWorkflowId` (aceita URL do editor n8n em qualquer parâmetro `workflow_id`), os helpers de sumarização (`SummarizeWorkflowListItem`, `BuildWorkflowChangeSummary`, `SummarizeExecution`), `GuardPagination` (teto de páginas + detecção de cursor repetido, usado em todo loop `while(cursor)`) e o exemplo `FilterJsonExample` compartilhado nas descrições. Os wrappers de backup (`BackupWorkflowAsync`/`BackupDataTableAsync`, dentro de `BackupTools`) chamam o `BackupService` apenas quando a IA invoca `backup_workflow`/`backup_data_table` explicitamente — não há chamada automática antes de operações destrutivas (ver seção "Economia de tokens").
  - `McpOptions.cs` — vincula a seção de configuração `N8n` (`Url`, `ApiKey`, `BackupDir`, `PublicBaseUrl`).
  - `BackupService.cs` — salva snapshots JSON em disco (`BackupDir`, padrão `backups/` na raiz do host) quando `backup_workflow`/`backup_data_table` são chamados, lista esses arquivos, lê e exclui um arquivo específico. O nome do arquivo inclui o nome sanitizado do item (workflow/tabela), o ID e um sufixo aleatório de 6 chars hex, ex: `20260711-153000123-workflow-MeuFluxo-abc123-a1b2c3.json` — o timestamp tem precisão de milissegundo e o sufixo aleatório evita colisão silenciosa entre dois backups do mesmo item feitos muito próximos um do outro. A sanitização (`SanitizeForFileName`) mantém só `[A-Za-z0-9-_]` (colapsando o resto em `_`) porque o nome do arquivo também vira parte da URL de download, então precisa ser seguro em disco e em URL sem depender de encode/decode. Os métodos `Save*BackupAsync` retornam apenas o **nome do arquivo** (não o caminho absoluto do disco do servidor — inútil quando o cliente MCP roda em outra máquina); `ResolveBackupPath` e `DeleteBackup` reaplicam a mesma defesa contra path traversal (`Path.GetFileName`) usada em `ReadBackupAsync` — a primeira devolve o caminho físico (ou `null`) para o endpoint de download servir o arquivo, a segunda apaga o arquivo e devolve `bool` indicando se ele existia.
  - `Shell/` — família de tools MCP independente da API do n8n: executa comandos no shell do sistema operacional onde o servidor está rodando (ver seção "Ferramentas de shell" abaixo).
- **N8nMcpHttp** (`src/Backend/N8nMcpHttp`) — o host ASP.NET Core (`Microsoft.NET.Sdk.Web`, único lugar do repo com FrameworkReference implícito ao ASP.NET Core). O `Program.cs` configura o Serilog (`MinimumLevel.Is`/`Override` explícitos + `UseSerilogRequestLogging()`), registra `IRequestContext`→`HttpRequestContext`, o `McpClient` via `AddHttpClient`, registra o `BackupService` e o `ShellCommandRunner` como singletons, registra cada família de tools via `.WithTools<>()` condicionalmente por configuração (`Tools:*:Enabled`) e, condicionalmente (`Shell:Enabled`), o `ShellTools`, monta o pipeline de autenticação (ver "Autenticação" abaixo), mapeia o endpoint MCP em `/mcp`, os endpoints `/api-key`, um `GET /backups/{fileName}` para download de backups (ver seção de backup remoto abaixo) e um `GET /health` aberto (liveness para container). Contém também:
  - `McpApiKey.cs` — o contrato do header: `HeaderName = "x-api-key"` e o **único** lugar que conhece a ordem dos valores dentro da key (`[mcpApiKey, n8nUrl, n8nApiKey]`), via `FromValues`/`ToValues`. `ToValues` descarta os vazios do fim, então uma key só com a chave MCP não carrega separadores inúteis.
  - `McpAuthOptions.cs` — vincula `McpAuth:ApiKeys`, a lista de chaves MCP autorizadas.
  - `Middleware/McpApiKeyMiddleware.cs` — ver "Autenticação" abaixo.
  - `Endpoints/ApiKeyEndpoints.cs` — `POST /api-key/generate` e `POST /api-key/decode`. São POST para os segredos irem no corpo, nunca na URL; `generate` responde `400` sem `mcpApiKey` (uma key sem ela nunca passaria no middleware) ou quando `ApiKeyGenerator.Generate` lança `ArgumentException`, e `decode` responde `400` com `"API Key inválida."` quando `TryParse` falha.
  - `wwwroot/index.html` — página pública (servida por `UseDefaultFiles`/`UseStaticFiles`) que gera e decodifica a key chamando os dois endpoints. Pede a chave MCP no passo 1 para mandá-la no header; descobre a base URL de `location.href` (sem query/hash e sem `index.html`), então funciona atrás de proxy com prefixo, e monta a URL do MCP com `new URL('mcp', baseUrl)`. Mostra o comando `claude mcp add` pronto e instruções para Copilot Studio e Claude Web. Nada é persistido no navegador.
  - `Middleware/McpTrafficLoggingMiddleware.cs` — registra os corpos e cabeçalhos completos de requisição/resposta para chamadas `POST /mcp` (redigindo os cabeçalhos `x-api-key`, `X-N8N-API-KEY` e `Authorization`, e o campo `password` do corpo — usado por `execute_shell_command`), fazendo buffer de ambos os streams para que possam ser lidos e reproduzidos; requisições `GET /mcp` (o canal SSE do transporte MCP, que fica aberto por toda a sessão) não são bufferizadas, só logadas no início, para não acumular o stream inteiro em memória.

## Autenticação (header `x-api-key`)

`McpApiKeyMiddleware` é um middleware clássico (não filtro MVC, não `AuthenticationHandler`, não `[Authorize]` — não há `AddAuthentication`/`AddAuthorization` no projeto), registrado dentro de `UseWhen` por prefixo de rota e parametrizado pelo enum `McpKeyFormat` passado como argumento de construtor:

- `/mcp` e `/backups` → modo **`Encoded`**: o header é a key composta do `GeraApiKey`; é decodificada e só o 1º valor (a chave MCP) é confrontado com `McpAuth:ApiKeys`.
- `/api-key` → modo **`Raw`**: o header é a chave MCP **em texto puro**, porque esses endpoints são justamente quem produz/desfaz a key composta.

É *fail-closed*: `McpAuth:ApiKeys` vazia rejeita tudo com `401`, e o `Program.cs` loga um aviso no boot nesse caso. A comparação usa `CryptographicOperations.FixedTimeEquals` iterando **todas** as chaves com `|=`, sem short-circuit na primeira coincidência. Usa `IOptionsMonitor` (`CurrentValue`), então editar `McpAuth:ApiKeys` no `appsettings.json` vale sem reiniciar. Rejeição devolve `401` + `{ "error": ... }` e loga o motivo, nunca a chave.

Ordem no pipeline importa: estáticos **antes** dos `UseWhen` (senão a própria página exigiria o header que ela serve para gerar), `UseRateLimiter` antes deles (para o `429` vir antes do `401`), em `/mcp` o traffic logging **antes** da autenticação (registra também as rejeitadas) e em `/api-key` **sem** traffic logging, de propósito, para a API key do n8n do corpo do `generate` não cair no arquivo de log. Abertos ficam só `/`, os arquivos estáticos e `/health`.

O rate limit (`AddRateLimiter`) é um **`GlobalLimiter`** particionado por `RemoteIpAddress`, em janela fixa de 1 minuto: `RateLimit:ApiKeyPermitsPerMinute` (padrão 10) em `/api-key`, `RateLimit:McpPermitsPerMinute` (padrão 300) em `/mcp` e `/backups`, `GetNoLimiter` no resto. Tem de ser o `GlobalLimiter` e não `RequireRateLimiting` no endpoint: os `UseWhen` de autenticação rodam antes do roteamento, então uma política por endpoint só seria avaliada depois do `401`. Atrás de reverse proxy sem forwarded headers, o IP visto é o do proxy e tudo cai na mesma partição.

## Resolução do destino n8n (override por requisição)

`McpClient.ResolveTarget()` escolhe a URL da instância n8n e a API key com a seguinte precedência, verificada a cada requisição:

1. 2º e 3º valores do header `x-api-key` (via `IRequestContext.N8nUrl`/`N8nApiKey`, implementado no host por `HttpRequestContext`, que decodifica o header já validado pelo middleware)
2. `N8n:Url` / `N8n:ApiKey` da configuração (`appsettings.json`, vazio por padrão — definido via `appsettings.Development.json`, variáveis de ambiente ou user secrets)
3. Variáveis de ambiente `N8N_URL` / `N8N_API_KEY`, aplicadas por `PostConfigure<McpOptions>` quando o passo 2 está vazio — permite subir o container só com variáveis

URL e credencial são resolvidas de forma independente (pode vir URL da key e API key da configuração). Isso significa que uma única instância do servidor implantada pode apontar para diferentes instâncias do n8n a cada chamada, bastando gerar uma key com esses valores — não há uma configuração fixa de tenant único. Quando a key não os traz e nada está configurado, `ResolveTarget` lança `InvalidOperationException` em vez de cair silenciosamente em um destino errado.

Os headers `X-N8N-URL`/`X-N8N-API-KEY` **não são mais lidos** (a credencial vem dentro da key); `X-N8N-API-KEY` continua sendo o header que o `McpClient` envia **ao n8n**, e segue na lista de redação do log caso algum cliente antigo ainda o mande.

Consequência de segurança: como a key carrega a API key do n8n, quem detém a key age no n8n com aquela credencial. Em conector compartilhado (Claude Web, Copilot Studio), todos os usuários do conector agem com a mesma credencial.

## Tratamento do payload de workflow

A API de criação/atualização de workflow do n8n só aceita `name`, `nodes`, `connections`, `settings` — qualquer outro campo é rejeitado. `McpClient.FilterWorkflowPayload` reduz um objeto JSON de workflow a apenas esses campos antes de toda chamada de criação/atualização/duplicação, e dentro de `settings` mantém só as chaves da whitelist `AllowedSettingsKeys` (`saveExecutionProgress`, `saveManualExecutions`, `saveDataErrorExecution`, `saveDataSuccessExecution`, `executionTimeout`, `errorWorkflow`, `timezone`, `executionOrder`, `callerPolicy`, `callerIds`) — o n8n rejeita `settings` com chaves fora dessa lista. `UpdateWorkflowAsync` e `DuplicateWorkflowAsync` primeiro fazem um `GET` do workflow atual, mesclam apenas os campos alterados e então enviam o payload filtrado via `PUT`/`POST` — as atualizações parciais são implementadas no lado do cliente, não pela API do n8n.

Como consequência inerente dessa restrição da API, `staticData` (estado de polling/dedup) e `pinData` não podem ser reenviados e são perdidos por qualquer `update_workflow`/`update_workflow_node`/`add_workflow_node`/`delete_workflow_node`/`rename_workflow_node`. Não há como evitar isso client-side; `McpClient.AttachDataLossWarningIfNeeded` pelo menos avisa (`_dataLossWarning` na resposta, exposto como `dataLossWarning` no resumo do `WorkflowTools`) quando o workflow tinha esses campos antes da edição.

## Convenção de parâmetros de ferramentas

Parâmetros que representam estruturas JSON (nodes, connections, settings, filtros, linhas) são tipados diretamente como `JsonObject`/`JsonArray` — o SDK MCP (`ModelContextProtocol.Core` 1.4.1) gera o schema `"type":"object"`/`"array"` a partir deles e faz o bind/validação da entrada antes de invocar o método C#, então o modelo não precisa mais escapar JSON dentro de JSON. Todas as descrições de ferramentas e mensagens de erro estão em português (pt-BR), alinhadas ao público-alvo.

## Economia de tokens

O servidor foi desenhado para minimizar o volume de JSON trocado com a IA, sem reduzir o que ela consegue fazer:

- **Respostas resumidas por padrão**: `list_workflows` retorna um resumo por item (`id`, `name`, `active`, `createdAt`, `updatedAt`, `tags`, `nodeCount`) em vez do workflow completo; `get_workflow` omite `pinData`/`staticData`/`meta`/`shared` a menos que `full=true`; `list_executions`/`get_execution` retornam um resumo (`id`, `status`, `workflowId`, `mode`, `startedAt`, `stoppedAt` e, se houver erro, `errorNode`/`errorMessage`) a menos que `include_data=true` — o payload completo só é baixado da API quando explicitamente pedido ou, item a item, apenas para execuções com `status=error` (para extrair o erro), nunca para a página inteira por padrão. As ferramentas de escrita de workflow (`create_workflow`, `update_workflow`, `duplicate_workflow`, `set_workflow_active` e as de edição de node) retornam um resumo compacto (`id`, `name`, `active`, `nodeCount`, `nodes`) em vez do workflow inteiro.
- **URL do editor aceita como ID**: todo parâmetro `workflow_id` aceita tanto o ID quanto a URL do editor n8n (`ResolveWorkflowId` em `McpToolsHelpers.cs` extrai o segmento após `/workflow/`).
- **Edição granular de node** (`update_workflow_node`, `add_workflow_node`, `delete_workflow_node`, `rename_workflow_node`): a IA envia só o nome do node e o delta (ex: `{"parameters":{"url":"..."}}`), e o servidor faz o GET, aplica a mudança em memória (merge profundo, rewire de `connections` preservando o índice de saída/ramo de origem — importante para não fundir ramos de IF/Switch — e sem afetar conexões de IA não relacionadas, substituição de expressões `$('Nome')`) e o PUT — evitando reenviar o array `nodes` inteiro a cada alteração pequena.
- **Backup sob demanda, não automático**: o servidor não faz backup automaticamente antes de operações destrutivas — isso gerava um backup a cada passo de uma sequência de alterações, mesmo quando desnecessário. A política de quando efetivamente oferecer o backup ao usuário (perguntar via `AskUserQuestion` mostrando a data do último backup, e oferecer uma única vez no início de uma sequência de alterações no mesmo fluxo/tabela em vez de a cada passo) é implementada do lado do cliente, na skill `n8n` (fora deste repositório), não no servidor. Quando `backup_workflow`/`backup_data_table` são chamados, o `BackupService` salva um snapshot em `backups/` e devolve o nome do arquivo (`backupFile`) e um link de download (`backupUrl`) — o conteúdo do backup nunca passa pela janela de contexto da IA. `list_backups` é paginado (`limit`/`cursor`) e devolve `baseUrl` uma vez (concatenar com `fileName` de cada item) em vez de repetir a URL completa por item. `restore_workflow_backup`/`restore_data_table_backup` permitem reverter só com o nome do arquivo, sem precisar baixar o conteúdo. `delete_backup` exclui permanentemente um ou mais arquivos de backup (nomes separados por vírgula, sem exclusão por filtro/substring — de propósito, para não permitir apagar em massa por engano), reportando quais foram excluídos e quais não foram encontrados.
- **Buscas compostas com teto**: `find_in_workflows` pagina por todos os workflows no servidor e retorna só os workflows/nodes que casaram com o texto procurado (até `max_results`, com `truncated` na resposta), evitando N chamadas de `get_workflow` e evitando despejar centenas de KB para um termo comum. `list_data_tables` com filtro por `name` também pagina por todas as tabelas do servidor (não só a primeira página) para não devolver vazio com muitas tabelas cadastradas. `set_workflow_tags` (a versão por ID foi removida por redundância) resolve nomes de tag para IDs (criando as que faltarem) e chama `SetWorkflowTagsAsync` em uma única ferramenta. Todo loop de paginação (`GuardPagination`) tem um teto de páginas e detecta cursor repetido, abortando em vez de rodar indefinidamente.
- **Tools consolidadas**: `activate_workflow`/`deactivate_workflow` → `set_workflow_active(bool)`; `update_data_table_rows`/`upsert_data_table_rows` → `update_data_table_rows(..., upsert: bool)`; `get_workflow_node` → parâmetro opcional `node_name` de `get_workflow_nodes`.

## Backup remoto: download por URL e restauração de data table

Pensado para o cenário em que o servidor MCP está hospedado remotamente e o cliente MCP roda em outra máquina, onde um caminho de disco local do servidor (o que `backupFile` devolvia antes) não serve para nada:

- **Download do backup**: `backup_workflow`/`backup_data_table` retornam `backupFile` (nome do arquivo, usado para restaurar) e `backupUrl` (URL completa para baixar o conteúdo). `list_backups` traz `baseUrl` uma vez (ver "Economia de tokens" acima). A URL é montada em `BackupTools.BuildBackupUrl`/`BuildBackupsBaseUrl`: usa `N8n:PublicBaseUrl` se configurado (útil atrás de reverse proxy sem forwarded headers), senão deriva `scheme://host` da própria requisição MCP recebida via `IRequestContext.GetRequestBaseUrl()`.
- **Endpoint de download** (`Program.cs`, `GET /backups/{fileName}`): serve o arquivo direto do disco se existir (`404` caso contrário), mas **exige o header `x-api-key`** no mesmo modo `Encoded` do `/mcp` (`401` sem ele) — o link não abre direto no navegador, precisa de um cliente que mande o header (`curl -O -H "x-api-key: ..."`). As descrições de `backup_workflow`/`backup_data_table`/`list_backups` avisam isso.
- **Restauração de data table**: `restore_data_table_backup` (paralelo ao já existente `restore_workflow_backup`) faz uma **substituição total** — recria a tabela do zero com as colunas e linhas exatas do backup (sempre gerando um novo ID, mesmo padrão de `restore_workflow_backup` ao recriar um workflow excluído) e só então exclui a tabela antiga (se ainda existir): cria e reinsere as linhas **antes** de excluir, para que uma falha no meio do caminho não deixe o backup sem tabela nenhuma (a tabela original só é removida depois que a nova já está populada com sucesso). As linhas são reinseridas em lotes de até 250, removendo antes os campos gerados pelo n8n (`id`, `createdAt`, `updatedAt`) via `StripRowMetadata`.
- **Detecção de "não existe mais"**: tanto `restore_workflow_backup` quanto `restore_data_table_backup` decidem "recriar em vez de atualizar/excluir" checando `N8nApiException.StatusCode == HttpStatusCode.NotFound`, não mais uma checagem frágil de substring `"404"` na mensagem de erro (que podia disparar por acidente se o corpo do erro contivesse esse texto por outro motivo).

## Ferramentas de shell

`McpToolkit/Shell/` expõe duas tools MCP independentes da API do n8n, para executar comandos no shell do sistema operacional onde o servidor está hospedado (não na máquina do usuário): `execute_shell_command` e `get_shell_info` (`ShellTools.cs`). São **desligadas por padrão** (`Shell:Enabled = false` no `appsettings.json`) — como a imagem deste MCP é publicada no Docker Hub e pode ficar exposta remotamente, ligar a execução de comandos é uma decisão explícita de quem sobe a instância, feita via `Shell:Enabled = true` na configuração. Com `Enabled = false`, as duas tools nem aparecem no `tools/list` (checado direto na configuração em `Program.cs`, antes de `.WithTools<ShellTools>()`).

- **Resolução de shell** (`ShellResolver.cs`): Windows → PowerShell (`pwsh` no PATH, senão `powershell.exe`) ou `cmd.exe`; Linux/macOS → `bash` ou `sh`. Quando o chamador pede `shell = "auto"`, a precedência é `Shell:DefaultShell` configurado (se diferente de `Auto`) e só então o padrão do SO. UTF-8 é forçado nos dois shells do Windows (`[Console]::OutputEncoding=...` no PowerShell, `chcp 65001` no cmd).
- **Execução** (`ShellCommandRunner.cs`): roda o comando via `Process`, captura stdout/stderr, nunca lança exceção por exit code não-zero (isso é um resultado legítimo, devolvido em `exitCode`/`stdErr`). Timeout é sempre um teto (`Shell:TimeoutSeconds`, `Math.Min` com o valor pedido pelo chamador) e mata a árvore de processos ao estourar OU quando o chamador cancela a chamada (antes só matava no caso de timeout, deixando o processo órfão em cancelamento), retornando `timedOut: true` e `exitCode: -1` quando é timeout. Saída é truncada incrementalmente durante a execução (não só no final), limitando o acúmulo em memória mesmo com um comando que produz saída ilimitada (`yes`, `find /`) durante todo o timeout; o `WaitForExit()` final é limitado a 5s para não travar indefinidamente se um processo neto herdou os handles dos pipes.
- **Guard-rails** (`ShellOptions`, seção `Shell`): `AllowedCommands`/`BlockedCommands` verificam o executável de **cada segmento** do comando (dividido por `;`, `&&`, `||`, `|`, `&` e por quebra de linha), não só o primeiro — ainda assim não é uma sandbox (quoting, subshells e `powershell -c "..."` contornam a checagem). `Password`, se configurada, é exigida em `execute_shell_command` (comparação em tempo fixo via `CryptographicOperations.FixedTimeEquals`); `get_shell_info` nunca exige senha.
